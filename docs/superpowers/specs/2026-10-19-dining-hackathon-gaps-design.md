## 0. 왜 하는가

v2로 신청 → 자동 매칭·재배치·확정 → 식당 배정 → 앱 단체방 자동 생성 → 리마인드·대화 콘텐츠 → 체크인·피드백 → 다음 매칭 반영까지 이미 돈다.
남은 구멍은 **돈과 사람 손**이다. 계좌이체 입금을 운영자가 건별 승인하고, 이용권 체계가 해커톤 기준과 다르고, 취소·노쇼 정책이 비어 있고, CS를 사람이 다 받는다.
PRD 핵심 질문("운영자의 수고를 어떻게 줄일까")에 대한 답을 이 네 개로 메운다.

### 목표
1. 계좌이체 입금 → 결제 완료가 운영자 클릭 없이 된다.
2. 해커톤 가격·멤버십 규칙대로 이용권을 판다.
3. 환불 마감·당일 취소·노쇼 보증금 정책이 앱에서 자동 적용된다.
4. 1:1 문의방에 AI가 먼저 답하고, 모르는 것만 운영자에게 넘긴다.
5. PRD 18장 데모 시나리오가 실서비스에서 끊김 없이 돈다(작은 P0 갭 포함).

### 비목표
- 실 PG 연동(PAY-04), 은행 API 송금. 환불·보증금 반환의 **실제 송금**은 운영자가 한다.
- 서울 4개 지역 외 지역.
- 매칭 엔진 알고리즘 변경(가중치·성비 규칙은 v2 그대로).

### 안티골
- 실사용자 데이터에 심사용 테스트 데이터가 섞여 보이는 것.
- AI가 돈·제재에 손대는 것, 다른 참가자 정보를 말하는 것.
- 입금 자동 대사가 틀린 사람을 결제 완료시키는 것(애매하면 반드시 예외함).

## 2. 입금 자동 대사 (MacroDroid 웹훅)

### 2.1 흐름
```
은행앱 입금 푸시 ─(MacroDroid 알림 트리거)→ POST /api/payments/deposit-webhook
   헤더 X-Deposit-Secret: ${DEPOSIT_WEBHOOK_SECRET}
   바디 {"text": "<알림 원문>", "receivedAt": "<MacroDroid 시각, 선택>"}
→ deposit_notifications 저장(원문·수신시각·해시, UNIQUE(hash))  ← 중복 알림은 여기서 걸러 200 반환
→ 파서: 원문에서 (입금자명, 금액) 추출. 실패 → ExceptionCase(PAYMENT, "파싱 실패")
→ 대사: 결제 대기 건 중 (payer_name == 입금자명 AND expected_amount == 금액)
     1건 → 그 건 결제 완료(아래 2.3), notification.matched_target 기록
     0건/2건+ → ExceptionCase(PAYMENT), 원문·후보 목록 첨부
```

### 2.2 결제 대기 건 = "신청 1건에 기대 입금액 1개"
신청 하나당 입금은 한 번이다. 기대 금액 = (이번에 새로 사는 이용권 가격, 없으면 0) + (보증금 대상이면 50,000).
- 1회권 신규: 9,900 / 보증금 대상 59,900
- 멤버십 보유자: 0 → 입금 불필요, 즉시 결제 완료 / 보증금 대상이면 50,000
- 멤버십 신규 구매 + 신청: 멤버십 가격 (+50,000)
- 신청 없이 멤버십만 구매: 멤버십 가격

`payer_name`은 결제 대기 생성 시점의 회원 실명(`User.name`)으로 고정 저장한다. 결제 화면에 "입금자명은 반드시 ○○○(실명)" 강조.

### 2.3 결제 완료 처리
기존 `AdminTicketService.confirm(passId)`의 본문(이용권 activate → ISSUE 거래 → 결제 대기 신청 자동 확정·차감 → `ApplicationConfirmedEvent`)을 서비스 메서드로 끌어내 **운영자 버튼과 웹훅이 같은 코드**를 탄다. 보증금이 포함된 건이면 보증금 레코드도 `PAID`로. 처리 주체(SYSTEM_WEBHOOK / adminId)를 거래 메모에 남긴다.

### 2.4 보안·운영
- 시크릿 불일치 401. 엔드포인트는 인증 필터 예외 경로. 요청 바디 크기 제한.
- 파서는 우리WON뱅킹 정규식 1개(샘플은 14장).
- 폰이 꺼져 알림이 안 오면 결제 대기로 남고 기존 운영자 승인 화면이 백업. 예외함 PAYMENT 건에서 "이 신청에 연결" 액션 = 같은 결제 완료 처리.
- 결제 기한(`paymentDeadline`) 지난 대기 건은 대사 후보에서 제외(기존 기한 로직 유지).

## 3. 이용권: 1회권 + 기간제 멤버십

### 3.1 모델
`TicketProductOption`에 `kind (COUNT | PERIOD)`, `periodMonths NULL` 추가. `TicketPass`에 `validUntil NULL`, `extendedDays INT DEFAULT 0` 추가.
- 상품 시드(마이그레이션): `1회권 9,900 COUNT 1`, `멤버십 1개월 35,000 PERIOD 1`, `3개월 75,000 PERIOD 3`, `6개월 120,000 PERIOD 6`. 기존 1회권 8,000·4회권은 **판매 중지**(soft delete). 이미 산 이용권은 그대로 유효.
- PERIOD 이용권: 결제 완료 시 `validUntil = activatedAt + periodMonths`. 신청 시 차감 없음(거래 기록은 `USE` 0으로 남겨 신청↔이용권 연결 유지 — 도메인 규칙 "remainingCount 변경 시 TicketTransaction"과 충돌 없음).
- 사용 가능 판정: COUNT는 `remainingCount > 0`, PERIOD는 `now <= validUntil` 이고 **같은 주(월~일, 회차 날짜 기준)에 이미 활성 신청이 없을 것**. 희망 회차 복수 선택 시 모든 후보 회차가 같은 주여야 한다(아니면 신청 거부 + 안내).
- 만료 스케줄러: 매일 `validUntil` 지난 PERIOD 이용권 `EXPIRE` 거래 기록.

### 3.2 매칭 실패 기한 연장
멤버십 신청이 `ALTERNATIVE_OFFERED` 또는 `NO_MATCH`가 되는 시점(v2 4.5-4)에 해당 이용권 `validUntil += 7일`, `extendedDays += 7`, `EXTEND` 거래 기록. 신청당 1회만(멱등). *연장 단위 7일은 내 판단(주 1회 모임 기준).*
멤버십의 `MatchResolution` 선택지: 대체 일정 / 보관(=연장으로 이미 보상, 신청 취소). 환불은 3.3 규칙을 따른다.

### 3.3 환불 규칙
| 이용권 | 환불 가능 조건 |
|---|---|
| 1회권 | 화 24:00(=매칭 실행) 전 취소, 또는 매칭 실패 후 환불 선택 |
| 멤버십 | 첫 `ATTENDED` 전까지 전액. 이후 불가 |

환불 흐름(v2 4.8 REFUND 확장): 환불 선택 → **계좌 입력(은행·계좌번호·예금주)** → `REFUND_REQUESTED → REFUND_PROCESSING`. 어드민 "송금 목록"에서 운영자가 실제 이체 후 일괄 `REFUNDED` 처리. *실서비스에서 송금 전에 "환불 완료"라고 보여주지 않기 위한 내 판단.* 데모 회원 건은 즉시 `REFUNDED`(14장). 계좌는 해당 환불 건에만 저장하고 완료 30일 후 마스킹.

## 4. 취소·노쇼·보증금

### 4.1 시점 정의 (회차 기준, 모두 Asia/Seoul)
- **마감** = 회차 주 화요일 24:00 = `applyDeadlineAt` = `matchRunAt`. 회차 생성 모달의 기본값을 이 규칙으로 계산(운영자가 바꿀 수는 있음).
- 마감 전 취소: 1회권 복원 또는 환불 선택, 보증금 반환.
- 마감 후 ~ 전날 취소: `CANCELED_LATE`, 환불 없음, 보증금 **반환**, 제재 없음. *당일만 제재라는 사용자 결정에 맞춘 내 해석.*
- 당일(회차 날짜 00:00 이후) 취소: `CANCELED_LATE` + **노쇼와 동일 취급**(보증금 몰수, 보증금 대상 지정).
- 취소 화면에 지금 시점에 적용되는 결과(환불 여부·보증금·제재)를 버튼 위에 먼저 보여준다(PAY-02).

### 4.2 노쇼
v2 그대로 회차 종료 +1시간에 체크인 없는 사람을 노쇼 **후보**로 표시, 운영자가 확정(FDB-01). 확정 시(또는 당일 취소 시) `User.depositRequired = true`(영구), 해당 신청 보증금 `FORFEITED`. 1회권은 이미 차감 상태 유지, 멤버십은 연장 없음.

### 4.3 보증금 레코드
`deposits`: `id, application_id UNIQUE, amount(50,000), status (PENDING | PAID | RETURN_PENDING | RETURNED | FORFEITED), return_bank, return_account, return_holder, created_at, updated_at`.
- 보증금 대상 사용자가 신청하면 생성. 반환 계좌는 신청(결제) 화면에서 입력 필수.
- 체크인 → `RETURN_PENDING`. 매칭 실패(해결 선택 완료 시)·마감 전/후 사전 취소 → `RETURN_PENDING`. 노쇼 확정·당일 취소 → `FORFEITED`.
- 어드민 "송금 목록"(3.3 환불과 같은 화면, 탭 분리)에서 운영자 이체 후 `RETURNED`.
- 매칭 후보 조건에 "보증금 대상이면 보증금 PAID" 추가.

### 4.4 확정 후 인원 부족 (Q6)
v2 4.7 `rebalance` 마지막 단계를 `ExceptionCase(CONFLICT)` 대신 **남은 멤버 각자에게 `MatchResolution` 생성**으로 바꾼다. 테이블은 `DISSOLVED`, 단체방에 시스템 공지. 이 경우 남은 사람은 본인 잘못이 아니므로 **마감 후여도 환불 선택지 허용**(1회권 환불·멤버십 기한 연장, 보증금 반환).

## 5. AI CS (1:1 문의방) — 그록봇 웹훅

2026-10-19 사용자 결정으로 OpenAI 직접 호출을 폐기하고 외부 에이전트 그록봇을 쓴다. 상세 동작·DB·API·테스트는 구현 계획 `Task BE-7`/`Task FE-5`가 기준이다. 요지:

- 고객 문의 저장 → 커밋 후 비동기로 `bot_dispatch` 생성(같은 방 10초 디바운스) → 서버가 **그 고객 본인 데이터만** 담은 페이로드로 그록봇 웹훅 발송(재시도 5s/30s/2m, 실패·3분 무응답이면 담당자 이관).
- 그록봇은 `POST /api/bot/replies`(전용 필터 체인, `WHATSUP_BOT_TOKEN` 상수 시간 비교, eventId 멱등, 오래된 답변 409)로 `reply` 또는 `handoff`만 할 수 있다. 데이터 변경 권한 없음.
- handoff·실패 시 방 `needsHuman` + 예외함 CS. 담당자가 직접 답하면 그 방 봇 일시정지(관리자만 해제). 고객당 시간당 20건·일 300건 상한, 관리자 전역 ON/OFF.
- 대상: `bot.enabled` && 전역 토글 && (허용 목록 || 데모 회원) && 방 일시정지 아님.

## 13. 빌더 체크 후 확정한 것

- **운영자 사전 승인 제거 (Q&A Q10).** 지금은 `randomTableEligibility != APPROVED`인 회원의 우연한 식탁 신청이 `PENDING`에 머물러 운영자 승인(`AdminApplicationService.approveRandomTableApplication`)을 기다린다. 신청 제출 시 제한 상태(`isRandomTableEligibilityRestricted`)가 아니면 **자동 APPROVED** 처리하고 곧장 결제 대기(또는 멤버십이면 결제 완료)로 넘긴다. 제한 회원은 기존처럼 거부.
- **마감 기준 회차** *(내 판단)*: 마감 = 회차 날짜 D-2의 24:00(목요일 회차면 화 24:00). 취소·환불 판정은 신청의 "현재 매칭 대상 회차"(배정 회차, 없으면 아직 지나지 않은 희망 회차 중 가장 이른 것) 기준.
- **멤버십 환불 위치** *(내 판단)*: 내 이용권 화면의 "멤버십 환불" 버튼(첫 ATTENDED 전만 노출). 진행 중 신청이 확정 전이면 함께 취소, 확정 테이블이 있으면 그 신청부터 취소해야 환불 가능(취소 규칙 4.1 적용).
- **멤버십 유효 판정** *(내 판단)*: 희망 회차 날짜 ≤ `validUntil`이어야 그 회차를 고를 수 있다.
- **입금 알림 중복 판정**: 원문에 초 단위 시각과 잔액이 들어 있으므로(14장 샘플) 해시 = 원문 그대로. 같은 사람이 같은 금액을 두 번 정상 입금해도 원문이 달라 둘 다 기록되고, 두 번째는 대사 후보가 없어 예외함으로 간다.
- **AI CS 적용 범위** *(내 판단)*: 모든 1:1 문의방. FAQ에 와썹하우스 일반 모임 기본(신청·입금·취소)도 짧게 포함. 모르면 사람에게 넘김.
- **체험 계정** *(내 판단)*: "체험 시작"을 누를 때마다 `isDemo` 회원을 새로 만든다(IP당 분당 3회 제한). 데모 회원은 숨김 종류만 보이고 일반 회원 목록·집계에서 빠진다. 해커톤 후 일괄 삭제. 공유 계정이면 한 심사위원의 노쇼가 다음 심사위원 시연을 깨기 때문.

## 14. 사용자 답변 (빌더 체크 후)

- **은행·알림 원문**: 우리WON뱅킹 입출금알림. 샘플(가명):
  ```
  [입금] 한지형        40,000원 1002-157-849***계좌 잔액 17,163,887원 09/18 13:19:30
  ```
  입금자명은 가림 없이 전체가 오고, 이름 뒤 공백 개수가 가변이다. `[출금]` 등 `[입금]`이 아닌 알림은 기록만 하고 무시. 파서 기준 정규식 예: `^\[입금\]\s+(.+?)\s+([\d,]+)원\s`. 은행이 입금자명을 일정 길이에서 자를 수 있으니 대사 비교는 "알림 이름이 `payer_name`과 같거나, `payer_name`의 앞부분"으로 하되 그때도 후보가 정확히 1건일 때만 자동 처리.
- **일반 모임도 자동 대사**: 같은 계좌를 쓰므로 일반 모임 신청의 결제 대기(`PAYMENT_PENDING`, 기대 금액 = 회차 가격, `payer_name` = 신청서 이름 — 비회원 포함)도 대사 후보에 넣는다. 결제 완료 처리는 기존 일반 모임 운영자 입금 확인과 같은 코드를 탄다. 2장의 "결제 대기 건"은 우연한 식탁·일반 모임 공통.
- **심사위원 결제 체험 = "심사용 입금 시뮬레이터" 카드** (구글시트 시연 안 함 — 운영이 앱 하나로 끝난다는 메시지와 충돌).
  - 데모 회원의 결제 대기 화면에만 노출. 제목 "심사용 입금 시뮬레이터", 설명 "실제로는 운영자 폰에 은행 알림이 오고, 와썹이 자동으로 확인합니다".
  - "N원 입금하기" 클릭 → 서버가 위 샘플 형식의 원문(입금자명·기대 금액 채움)을 만들어 **웹훅과 같은 대사 경로**로 넣고, 처리 결과(원문, 파싱 이름·금액, 연결 신청, 결과)를 응답.
  - 카드 안 작은 **"운영자 폰" 프레임**에 그 원문이 은행 푸시처럼 도착하는 연출 → 아래 ①알림 수신 ②이름·금액 확인 ③신청 연결 ④결제 완료 단계가 서버 결과대로 순서대로 체크 → 같은 화면 상태 카드가 결제 대기 → 결제 완료로 바뀜. 입금한 사람 폰에 "입금 알림"이 뜨는 것처럼 보이면 안 된다.
  - 데모 회원 건의 환불은 `REFUND_PROCESSING → REFUNDED` 즉시 자동 전환.
- **운영자 "입금 알림 로그" 페이지**: `deposit_notifications` 목록(최신순). 행마다 원문 → 파싱 이름·금액 → 연결된 신청(링크) → 결과(자동 완료 / 무시(출금 등) / 예외함 / 파싱 실패). 관리자 계정으로 들어간 심사위원의 보조 증거. 동명이인 예외 케이스 1건을 데모 시드에 넣어 "애매하면 예외함"도 보여준다.
- **실동작 증거**: 제출물에 실기기 30초 영상(실제 이체 → 알림 → 앱 결제 완료).
- **아이폰 대안 경로**: 웹훅은 원문만 받으므로 출처를 가리지 않는다. 안드로이드 MacroDroid(앱 푸시 원문)와 아이폰 단축어 자동화("메시지 수신 + '입금' 포함" → URL POST, 은행 **문자 알림** 원문)를 둘 다 받는다. 파서는 정규식 목록(푸시용 1개 + 문자용 1개)을 순서대로 시도. 문자 원문 샘플은 문자 알림 신청 후 추가 — 그전까지 문자용 정규식은 비워 두고 매칭 실패 시 파싱 실패 예외로 간다. 바디에 `source (MACRODROID | IOS_SHORTCUT | SIMULATOR)` 선택 필드.
- **심사위원 운영자 화면**: 실제 관리자 계정을 제공한다(사용자 결정). 빌더 작업: 심사 전용 관리자 계정을 새로 만들어(본인 계정 공유 아님) 제출 후 비활성화. ⚠️ 이 계정으로는 실회원 이름·연락처·신청 내역이 보인다. 데모 회원은 `isDemo`로 구분만 하고 어드민 권한 필터는 만들지 않는다.
